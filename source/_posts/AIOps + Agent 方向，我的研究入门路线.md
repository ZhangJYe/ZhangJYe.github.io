## 前言

最近我开始正式思考自己的研究方向：**AIOps + Agent**。

一开始听到这个方向时，我的感觉是：它很有前景，但也很抽象。AIOps 听起来像智能运维，Agent 听起来像大模型智能体。两个词放在一起，好像什么都能做：告警分析、日志排查、根因定位、自动修复、知识库问答、故障复盘、工单处理、变更风险分析……

但问题也来了：

> 作为一个科研初学者，我到底应该从哪里开始？  
> 是先看 AIOps 论文，还是先学 Agent 框架？  
> 是先做系统，还是先找创新点？  
> 最后怎么形成一个能发论文、能落地、能持续迭代的研究方向？

这篇文章不是最终答案，而是我当前阶段对 **AIOps + Agent 研究入门路线** 的一次梳理。

我希望它解决三个问题：

1. 我为什么选择 AIOps + Agent；
2. 这个方向到底要学什么；
3. 作为入门者，如何从读论文、做 Demo 到形成研究问题。

---

## 一、为什么选择 AIOps + Agent？

我选择这个方向，主要有三个原因。

### 1. AIOps 是真实工程问题

AIOps 不是一个纯概念方向，它背后有非常真实的工程场景。

在一个复杂线上系统中，每天都会产生大量运维数据：

- 指标：CPU、内存、QPS、延迟、错误率；
- 日志：错误日志、调用链日志、业务日志；
- Trace：服务调用链、Span、请求路径；
- 告警：监控系统产生的异常通知；
- 变更：发布、配置修改、扩容缩容、依赖升级；
- 工单和复盘：历史故障处理过程。

当系统规模变大后，人很难只靠经验快速判断：

```text
这个告警是不是重要？
这个异常是不是和刚才的发布有关？
根因可能在哪个服务？
应该先查日志、指标，还是链路？
有没有历史相似故障？
```

所以 AIOps 的核心价值在于：

> 用数据和智能方法，提升运维系统的感知、分析、决策和处置能力。

这本身就是一个很好的研究问题来源。

---

### 2. Agent 适合处理复杂运维任务

传统模型更擅长做单点任务，比如：

- 日志异常检测；
- 指标预测；
- 告警聚合；
- 根因分类；
- 故障文本分类。

但真实运维场景往往不是一个单点任务，而是一个复杂过程：

```text
收到告警
  ↓
理解告警含义
  ↓
查询相关指标
  ↓
检索相关日志
  ↓
分析最近变更
  ↓
查询历史案例
  ↓
生成可能根因
  ↓
给出排查步骤
  ↓
必要时调用工具执行操作
```

这个过程天然具有 **多步骤、多工具、多信息源、多轮推理** 的特点。

这正是 Agent 的优势场景。Agent 不只是回答问题，而是可以：

- 规划任务；
- 调用工具；
- 检索知识；
- 分析证据；
- 反思结果；
- 生成报告；
- 在一定边界内执行动作。

所以 AIOps + Agent 的结合点很自然：

> AIOps 提供真实复杂场景，Agent 提供任务编排和智能决策能力。

---

### 3. 这个方向兼具科研价值和工程落地价值

我不希望自己的研究方向只是停留在论文概念上，也不希望只做一个没有研究问题的工程 Demo。

AIOps + Agent 比较吸引我的地方在于，它既有工程系统可以做，也有研究问题可以挖。

比如：

- Agent 如何选择正确的运维工具？
- Agent 如何避免在故障分析中胡编？
- RAG 如何提升历史故障检索质量？
- 多 Agent 是否真的比单 Agent 更适合故障诊断？
- 如何评估一个 AIOps Agent 的效果？
- 如何让 Agent 的分析过程可解释、可追踪、可审计？
- 如何降低 Agent 调用工具的成本和延迟？
- 如何在真实运维数据稀缺的情况下构造评测集？

这些问题都不是简单堆 Prompt 就能解决的。

---

## 二、我对 AIOps + Agent 的初步理解

我现在把这个方向拆成三层：**数据层、能力层、决策层**。

---

### 1. 数据层：Agent 不能脱离运维数据

AIOps 的基础是数据。

| 数据类型 | 示例 | 作用 |
|---|---|---|
| Metrics | CPU、内存、延迟、错误率 | 判断系统状态 |
| Logs | 错误日志、业务日志 | 定位异常细节 |
| Traces | 调用链、Span | 分析服务依赖和请求路径 |
| Alerts | 告警名称、级别、时间 | 触发分析流程 |
| Changes | 发布、配置、扩容 | 判断故障是否由变更引起 |
| Tickets | 工单、故障单 | 沉淀历史经验 |
| Runbooks | 运维手册 | 指导排查步骤 |
| Postmortems | 故障复盘 | 提供历史案例 |

如果没有这些数据，Agent 就只能空谈。

所以 AIOps Agent 的第一步不是设计多复杂的智能体，而是先想清楚：

> Agent 能看到什么数据？  
> 数据从哪里来？  
> 数据质量如何？  
> 数据之间能不能关联？

---

### 2. 能力层：不是所有问题都要用 Agent

有了数据之后，需要构建不同能力。

例如：

```text
告警理解能力
日志摘要能力
指标异常分析能力
变更关联能力
历史案例检索能力
根因候选生成能力
排查步骤规划能力
故障报告生成能力
```

这些能力可以由不同技术实现：

- 规则；
- 传统机器学习；
- 深度学习模型；
- LLM；
- RAG；
- Tool Calling；
- Agent Workflow。

我现在的理解是：

> 能用规则稳定解决的，就不要硬上大模型。  
> 能用检索增强的，就不要让模型凭空记忆。  
> 需要多步骤推理和工具调用的，才适合用 Agent。

这也是做 AIOps + Agent 时需要保持克制的地方。

---

### 3. 决策层：Agent 的结论必须有证据

Agent 的核心价值不只是“会说”，而是能组织一个分析过程。

一个 AIOps Agent 的理想流程可能是：

```text
输入告警
  ↓
理解告警语义
  ↓
制定排查计划
  ↓
查询指标 / 日志 / 链路 / 变更 / 知识库
  ↓
整合证据
  ↓
生成可能原因
  ↓
给出排查步骤
  ↓
输出报告
  ↓
必要时进行人机协同确认
```

这里最重要的是：**Agent 的结论必须有证据**。

比如不能直接说：

> 这是数据库连接池耗尽导致的。

而应该说：

```text
可能原因：数据库连接池耗尽。

证据：
1. 10:32 开始接口 5xx 上升。
2. 同一时间段应用日志出现大量 connection timeout。
3. 数据库连接数接近 max_connections。
4. 最近 30 分钟没有发现服务发布记录。

建议：
1. 检查连接池配置。
2. 检查慢查询。
3. 临时扩容连接池或限流。
```

这就是 AIOps Agent 和普通聊天机器人的区别：

> 它必须基于证据，而不是基于感觉。

## 三、入门阶段需要补齐哪些知识？

作为科研初学者，我现在不能一上来就追求“提出一个很大的创新点”。

更合理的路线是先补基础。

---

### 1. AIOps 基础

我需要先理解 AIOps 的基本任务：

- 异常检测；
- 告警降噪；
- 告警关联；
- 根因定位；
- 故障预测；
- 自动修复；
- 故障报告生成；
- 变更风险分析。

其中，我最应该重点关注：

```text
告警分析
日志分析
根因定位
历史案例检索
故障报告生成
```

因为这些任务和 Agent 结合最自然。

---

### 2. 可观测性基础

AIOps 离不开可观测性。

我需要熟悉：

- Metrics；
- Logs；
- Traces；
- Prometheus；
- Grafana；
- OpenTelemetry；
- Jaeger；
- 常见告警规则；
- 服务依赖关系。

如果不懂可观测性，AIOps 很容易变成“拿日志随便喂给大模型”。

真正的问题是：

> 从哪些观测数据中提取证据？  
> 如何判断证据是否支持某个根因？  
> 如何把指标、日志、链路和变更关联起来？

---

### 3. LLM 与 Agent 基础

Agent 方向需要理解：

- Prompt Engineering；
- Tool Calling；
- Function Calling；
- RAG；
- Memory；
- Planning；
- Reflection；
- Multi-Agent；
- Agent Workflow；
- Guardrails；
- Evaluation。

但我不能只停留在框架使用层面。

我真正需要关注的是：

```text
Agent 为什么需要规划？
工具调用如何选择？
RAG 如何提供可靠证据？
多 Agent 是否真的有必要？
Agent 输出如何评估？
Agent 失败时如何回退？
```

---

### 4. RAG 基础

我认为 RAG 是 AIOps Agent 中非常核心的一环。

因为运维场景中有大量经验知识：

- 历史故障案例；
- 运维手册；
- 排查文档；
- FAQ；
- 架构说明；
- 工单记录；
- 复盘报告。

这些内容不应该完全靠模型记忆，而应该通过检索提供上下文。

RAG 需要重点学习：

- 文档切分；
- Embedding；
- 向量数据库；
- 召回；
- Rerank；
- Query Rewrite；
- Context Assembly；
- Citation；
- Recall@K 评估。

我现在尤其关注：

> 如何让 Agent 找到真正相关的历史案例，而不是只返回看起来相似的文本？

---

### 5. 后端系统能力

AIOps Agent 不是一个 Notebook Demo，它最终应该是一个系统。

所以我还需要补齐工程能力：

- Go 后端服务；
- API 设计；
- 任务队列；
- 缓存；
- 数据库存储；
- 向量数据库；
- 日志系统；
- 权限控制；
- 可观测性；
- 灰度与回滚；
- 成本控制。

这也是我选择这个方向的原因之一：它能把研究和后端工程结合起来。

## 四、A 会论文阅读路线

入门 AIOps + Agent，不能只看博客和框架文档，必须补一批代表性论文。

这里先按照“从 AIOps 基础到 Agent 结合”的顺序整理一份阅读路线。这里的 A 会主要指软件工程、系统、数据库、AI 和机器学习方向的高水平会议，例如 ICSE、FSE、KDD、WWW、CCS、NeurIPS、ICLR、ACL、IJCAI 等。

---

### 1. 日志分析与异常检测

日志是 AIOps 中最常见的数据源之一，很多故障诊断任务都要先理解日志。

建议先读：

1. **DeepLog: Anomaly Detection and Diagnosis from System Logs through Deep Learning**，CCS 2017  
   这篇论文是日志异常检测方向的经典工作，用深度学习建模日志序列，适合理解“日志序列如何用于异常检测”。

2. **LogRobust: Log-based Anomaly Detection on Unstable Log Data**，ESEC/FSE 2019  
   这篇论文关注日志不稳定问题，例如日志模板变化、字段变化等，对真实工程场景很有启发。

3. **LogAnomaly: Unsupervised Detection of Sequential and Quantitative Anomalies in Unstructured Logs**，IJCAI 2019  
   这篇论文同时考虑日志的序列特征和数量特征，适合理解日志异常检测中的不同建模角度。

读这些论文时，我应该重点关注：

- 输入数据是什么；
- 日志如何解析；
- 是否需要日志模板；
- 异常标签如何获得；
- 指标是什么；
- 和实际运维场景有什么距离。

---

### 2. 根因定位与微服务故障诊断

AIOps 最重要的任务之一是 Root Cause Analysis，也就是根因定位。

建议重点关注微服务场景，因为现代系统大多是分布式服务架构。

可以阅读：

1. **MicroRank: End-to-End Latency Issue Localization with Extended Spectrum Analysis in Microservice Environments**，WWW 2021  
   这篇论文关注微服务环境下的延迟问题定位，适合理解调用链和服务依赖如何用于定位故障。

2. **DiagFusion: Diagnosing Failures in Microservice Systems via Multimodal Data**，KDD 2023  
   这篇论文关注多模态运维数据融合，将日志、指标、Trace 等多源数据结合起来做故障诊断。它和 AIOps Agent 的方向非常接近，因为 Agent 也需要整合多源证据。

3. **Groot: An Event-graph-based Approach for Root Cause Analysis in Industrial Settings**，ICSE 2023  
   这篇论文关注工业场景中的事件图根因分析，适合理解如何把告警、事件和依赖关系组织成图结构。

阅读这些论文时，我要重点看：

- 是否使用多源数据；
- 如何表示服务依赖；
- 根因标签如何定义；
- 是否能解释诊断结果；
- 是否适合接入 Agent 的工具调用流程。

---

### 3. LLM for AIOps / Software Engineering

AIOps + Agent 不是简单地把大模型接到日志上，而是要理解 LLM 如何进入软件工程和运维流程。

可以重点读：

1. **ReAct: Synergizing Reasoning and Acting in Language Models**，ICLR 2023  
   这是 Agent 方向非常重要的一篇论文，提出将推理和行动结合起来。AIOps Agent 的工具调用、查询日志、查询指标，本质上都可以参考 ReAct 的思想。

2. **Toolformer: Language Models Can Teach Themselves to Use Tools**，NeurIPS 2023  
   这篇论文关注语言模型如何学习使用工具，对理解 Tool Calling 很有帮助。

3. **Reflexion: Language Agents with Verbal Reinforcement Learning**，NeurIPS 2023  
   这篇论文关注 Agent 的自我反思和迭代改进，对故障诊断中的“分析失败后如何修正”有启发。

4. **Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection**，ICLR 2024  
   这篇论文将检索、生成和自我反思结合起来，对 AIOps Agent 中“基于证据生成结论”很有参考价值。

这些论文不一定直接解决 AIOps 问题，但它们提供了 Agent 的基础机制：

- 推理与行动；
- 工具调用；
- 检索增强；
- 自我反思；
- 生成结果的可靠性控制。

---

### 4. RAG 与评估

RAG 是 AIOps Agent 的关键基础能力。

我需要重点关注：

- 文档如何切分；
- Query 如何改写；
- 检索结果如何排序；
- 上下文如何组装；
- 生成结果如何引用证据；
- 如何评估检索质量。

对我来说，最重要的不是一开始追求复杂模型，而是先建立一个简单可靠的评估闭环：

```text
构造问题集
  ↓
标注相关文档
  ↓
检索 Top-K
  ↓
计算 Recall@K
  ↓
分析失败案例
  ↓
优化切分、召回和重排
```

在运维场景中，Recall@K 尤其重要，因为：

> 漏掉关键证据，比多召回一些无关内容更危险。

## 五、我准备怎么入门？

我给自己设计了一个阶段路线。

---

### 阶段一：先理解 AIOps 场景

目标不是马上写论文，而是先理解问题。

我要做的事情：

1. 阅读 AIOps 综述和经典任务论文；
2. 梳理常见运维任务；
3. 整理 AIOps 数据类型；
4. 学习 Prometheus、日志、Trace 的基本概念；
5. 找几个典型故障场景进行分析。

阶段产出：

```text
一篇 AIOps 基础任务笔记
一篇可观测性数据类型笔记
一份典型故障排查流程图
```

---

### 阶段二：学习 Agent 基础能力

目标是理解 Agent 的工作方式。

我要做的事情：

1. 学习 Tool Calling；
2. 学习 RAG；
3. 学习 Agent Workflow；
4. 学习 ReAct、Plan-and-Execute 等基本思想；
5. 对比单 Agent 和多 Agent 的适用场景；
6. 尝试用 Claude Code、LangChain、Eino 做小实验。

阶段产出：

```text
一个最小 AIOps Q&A Agent
一个能调用工具的告警分析 Agent Demo
一篇 Agent 工程化笔记
```

---

### 阶段三：做一个最小 AIOps Agent 原型

不要一开始做全功能平台，先做最小闭环。

输入：

```json
{
  "alert_name": "HighErrorRate",
  "service": "order-service",
  "severity": "critical",
  "metrics": "...",
  "logs": "...",
  "changes": "..."
}
```

输出：

```json
{
  "summary": "故障现象总结",
  "evidences": ["证据1", "证据2"],
  "possible_causes": ["可能原因1", "可能原因2"],
  "troubleshooting_steps": ["步骤1", "步骤2"],
  "risk": "风险提示"
}
```

这个原型要满足几个要求：

- 不编造日志；
- 证据不足时说明不确定；
- 输出结构稳定；
- 可以检索历史案例；
- 可以调用简单工具；
- 可以保存分析过程。

阶段产出：

```text
一个最小可运行 Demo
一篇系统设计笔记
一份错误案例分析
```

---

### 阶段四：构建评测集

如果想做科研，不能只说“效果不错”。

必须回答：

> 怎么证明你的 Agent 更好？

所以需要构建评测集。

可以先从小规模做起：

- 20 个告警样例；
- 每个样例包含日志、指标、变更和标准答案；
- 标注期望根因；
- 标注相关文档；
- 标注合理排查步骤。

可以评估：

| 维度 | 指标 |
|---|---|
| 检索效果 | Recall@K |
| 根因分析 | Top-K Accuracy |
| 证据引用 | Evidence Precision |
| 输出质量 | 人工评分 |
| 稳定性 | 多次运行一致性 |
| 成本 | Token / 工具调用次数 |
| 延迟 | End-to-End Latency |

我现在比较关注 Recall@K，因为在运维场景中：

> 漏掉关键证据，比多召回一些无关内容更危险。

---

### 阶段五：寻找研究问题

等基础系统跑通之后，再考虑研究创新点。

可能的研究问题包括：

1. **面向 AIOps 的 Agent 证据约束机制**  
   如何让 Agent 的根因分析必须基于日志、指标和历史案例证据？

2. **面向故障诊断的多源上下文组装方法**  
   如何在有限上下文窗口内融合日志、指标、Trace、变更和知识库？

3. **AIOps Agent 的可靠性评估框架**  
   如何评估 Agent 的排查质量、证据质量和稳定性？

4. **基于历史案例检索的故障分析增强方法**  
   如何提升历史故障案例对当前告警分析的帮助？

5. **人机协同的 AIOps Agent 工作流**  
   哪些步骤适合 Agent 自动完成，哪些步骤必须让人确认？

这些问题相比“做一个 AIOps Agent 系统”更适合作为研究切入点。

## 六、我目前最想做的方向

目前我最感兴趣的是：

> 基于 RAG 和工具调用的 AIOps Agent 故障分析系统。

也就是让 Agent 在分析告警时，不是直接生成结论，而是先获取证据：

```text
告警信息
日志片段
指标趋势
服务依赖
最近变更
历史案例
运维文档
```

然后再基于这些证据输出结构化分析结果。

我希望系统具备这几个特点：

1. **证据驱动**：每个结论尽量对应证据；
2. **工具增强**：可以查询日志、指标、知识库；
3. **结构化输出**：方便前端展示和后续评估；
4. **可评测**：不是只看主观感觉；
5. **可扩展**：后续可以加入多 Agent 或自动修复；
6. **安全边界清晰**：高风险操作必须人确认。

## 总结

AIOps + Agent 是一个很适合长期投入的方向。

它既有真实的工程问题，也有值得研究的科学问题；既需要系统能力，也需要算法、LLM、RAG 和评估方法。

作为入门阶段，我不能一开始就追求“大而全”的系统，也不能只停留在“用大模型问答”的层面。

我更应该按照这样的路径推进：

```text
理解场景
  ↓
补齐基础
  ↓
做最小原型
  ↓
构建评测集
  ↓
寻找研究问题
  ↓
形成系统和论文贡献
```

对我来说，AIOps + Agent 的核心不是“让 Agent 替代运维工程师”，而是：

> 让 Agent 在复杂故障场景中，帮助人更快地组织信息、找到证据、形成判断、降低排查成本。

这是我目前对这个方向的起点理解，也是接下来一段时间的学习路线。
